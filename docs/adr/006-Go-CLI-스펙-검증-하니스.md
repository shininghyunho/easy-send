# ADR-006: Go CLI 피어는 프로토콜 스펙의 독립 검증 하니스다

- **상태**: 확정 (2026-08-16, Phase 2 완료)
- **결정**: Flutter 앱과 완전히 별개의 코드베이스로, Go 표준 라이브러리 중심의 CLI 피어(`go-cli/` — `ls`·`send`·`recv` 서브커맨드)를 만든다. 구현 시 앱 소스를 보지 않고 **프로토콜 스펙 문서(PRD 4장)만** 근거로 삼는다.
- **대가**: 유지할 구현이 하나 늘어난다. 스펙이 바뀌면(예: ADR-002 브로드캐스트 병행) Go도 따라 고쳐야 한다.

## 배경

프로토콜 스펙을 문서로 썼지만, 문서가 정말 자기완결인지(그 문서만 보고 다른 사람·다른 언어가 구현할 수 있는지)는 실제로 해보기 전엔 모른다. 또 Phase 3의 Rust 재구현(ADR-005)을 앞두고, Rust 코어가 맞게 동작하는지 판정해 줄 **기준 상대(reference peer)**가 필요했다 — 앱끼리만 테스트하면 양쪽이 같은 버그를 공유해도 통과해버린다.

## 검토한 대안

### ① 앱 하나로 충분, CLI 생략 — 기각

**기각 이유: 스펙 검증과 교차 검증을 둘 다 잃는다.** 단일 구현은 "스펙대로"가 아니라 "구현대로" 동작한다. 스펙 문서의 구멍(모호한 문구, 빠진 규칙)은 두 번째 독립 구현이 부딪혀야 드러난다.

### ② Dart로 테스트 클라이언트 작성 — 기각

기존 Dart 코어를 재사용한 스크립트로 앱을 검증하는 안. 만들기는 가장 싸다. **기각 이유: 독립 구현이 아니다.** 같은 코어를 공유하므로 코어의 버그·스펙 해석 오류를 그대로 물려받아 교차 검증 효과가 없다.

### ③ Go 독립 구현 — 채택

언어 선택 이유: 표준 라이브러리에 UDP·TLS·HTTP가 다 있어 의존성이 사실상 0이고(`golang.org/x/net`·`x/sys`만 추가), 단일 바이너리라 하니스로 돌리기 좋다. 학습 겸 목적에도 맞다.

원칙: 앱 소스 열람 금지, PRD 4장만 보고 구현. 결과는 앱과의 상호 전송 체크섬 일치로 판정한다.

## 결과

**얻는 것**

- **스펙 자기완결 실증**: 4장 문서만으로 구현한 Go 피어가 첫 빌드에서 앱과 상호 발견·양방향 전송(체크섬 일치)에 성공했다. 승인 타임아웃(408)·거절(403)·포트 폴백·TOFU 지속성도 라이브로 확인.
- **Rust 재구현의 심판 역할**: P3-1에서 Rust 코어는 Go CLI·Dart 코어·실기기 앱 3상대와 교차 전송으로 검증됐다. 독립 구현이 있었기에 "Rust가 스펙을 맞게 말하는가"를 앱 없이 판정할 수 있었다.
- 스펙의 숨은 전제도 드러났다: Dart의 "/24 가정" 브로드캐스트는 넷마스크를 못 얻는 런타임의 근사치일 뿐임이 명확해져, Go는 실제 넷마스크로 계산하도록 스펙 문구가 정리됐다.

**잃는 것 (감수)**

- 스펙 개정 시 구현 3개(Dart는 archive, 현재는 Rust·Go)를 동기화해야 한다.
- CLI의 `ls`·`send`는 일회 실행이라 수신 서버 없이 announce만 한다 — 상대 목록에 잠깐 잡혔다 TTL로 사라지는 특성은 도구 성격상 수용.
