# ADR-001: 프로토콜을 자체 설계하되, LocalSend v2의 구조를 참고서로 차용한다

- **상태**: 확정 (2026-08-15)
- **결정**: 와이어 프로토콜(탐색·전송·보안)을 직접 설계한다. 단 백지에서 시작하지 않고 LocalSend 프로토콜 v2의 구조(멀티캐스트 announce, prepare-upload → upload 2단계 전송, 지문 기반 신원)를 뼈대로 가져온다. LocalSend와의 호환은 목표가 아니며, 멀티캐스트 그룹(224.0.0.168)과 포트(53318)를 일부러 다르게 잡아 충돌을 피한다.
- **대가**: LocalSend 앱과는 서로를 발견하지도, 전송하지도 못한다. 프로토콜 문서(PRD 4장)를 스스로 유지해야 한다.

## 배경

이 프로젝트의 목표는 "LAN 파일 전송 앱을 갖는 것"이 아니라 **그 메커니즘을 설계하며 학습하는 것**이다. 그래서 "어느 수준까지 직접 만들 것인가"를 가장 먼저 정해야 했다. 완성품이 목표라면 LocalSend를 그냥 쓰면 되기 때문이다.

## 검토한 대안

### ① LocalSend 프로토콜 완전 호환 — 기각

LocalSend v2 스펙을 그대로 구현해 실제 LocalSend 앱과 상호 운용하는 안.

**기각 이유: 설계 경험이 사라진다.** 스펙이 이미 완성되어 있으므로 구현 연습만 남는다. 탐색 주기·TTL·세션 상태머신·에러 코드 같은 결정을 직접 내려보는 것이 이 프로젝트의 핵심 가치인데, 호환을 목표로 하면 그 결정권이 전부 스펙에 넘어간다.

### ② 완전 독자 설계 — 기각

기존 프로토콜을 전혀 보지 않고 백지에서 설계하는 안.

**기각 이유: 막혔을 때 참고서가 없다.** UDP 탐색과 TLS 신원 검증은 함정이 많은 영역이라(멀티캐스트를 버리는 공유기, 자체서명 인증서 검증 등), 검증된 선례 없이 설계하면 시행착오 비용이 학습 효과를 넘어선다.

### ③ 자체 설계 + LocalSend 구조 차용 — 채택

큰 구조(무엇을 주고받는가)는 LocalSend v2에서 가져오고, 세부(스키마 필드, 타이밍 값, 상태머신, 에러 코드)는 직접 결정한다. 결과물이 PRD 4장(프로토콜 스펙)이며, 이후 Go CLI(ADR-006)와 Rust 코어(ADR-005)가 이 문서만 보고 구현할 수 있었다 — 스펙이 자기완결임이 실증됐다.

## 결과

**얻는 것**

- 프로토콜의 모든 세부 결정을 직접 내리는 설계 경험. 막히면 LocalSend 소스가 참고서가 된다.
- 스펙 문서(PRD 4장)가 구현 계약이 되어, 같은 프로토콜을 말하는 피어를 다른 언어(Go·Rust)로 늘릴 수 있었다.

**잃는 것 (감수)**

- LocalSend 생태계와의 상호 운용. 이 앱끼리만 통신한다.
- 프로토콜 버그·모호함을 스스로 발견하고 스펙을 개정해야 한다(실제로 ADR-002의 브로드캐스트 병행이 그 사례).
