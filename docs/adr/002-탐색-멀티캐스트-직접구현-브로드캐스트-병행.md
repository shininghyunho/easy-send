# ADR-002: 탐색은 UDP 멀티캐스트 직접 구현 + 서브넷 브로드캐스트 병행으로 한다

- **상태**: 확정 (2026-08-15 설계, 2026-08-16 실기기 실측으로 브로드캐스트 병행 개정)
- **결정**: 기기 탐색은 mDNS 라이브러리 대신 UDP 멀티캐스트(그룹 224.0.0.168, 포트 53318)를 직접 구현한다. 같은 announce 패킷을 **서브넷 브로드캐스트(예: 192.168.0.255)로도 함께** 보낸다 — 멀티캐스트만으로는 크로스 기기 탐색이 안 되는 공유기가 흔하다는 것을 실측했기 때문. 그래도 안 되는 네트워크를 위해 IP 직접 입력 폴백을 둔다.
- **대가**: 소켓 바인딩·인터페이스 순회·TTL 관리를 전부 직접 다뤄야 하고, announce가 매번 2번씩 나간다(수신 측이 지문 기준 upsert로 중복을 흡수).

## 배경

같은 LAN의 기기를 서버 없이 찾으려면 "여기 나 있어"를 네트워크에 뿌리는 방법이 필요하다. 표준 답은 mDNS(멀티캐스트 DNS — AirDrop·프린터 발견에 쓰이는 프로토콜)이고 라이브러리도 많지만, 이 프로젝트는 학습이 목표라 추상화 수준을 정해야 했다.

## 검토한 대안

### ① mDNS 라이브러리 — 기각

**기각 이유: 라이브러리가 다 해줘서 학습량이 없다.** 서비스 등록·발견·TTL이 전부 라이브러리 안에서 일어나, "탐색이 어떻게 동작하는가"를 배울 수 없다. 또한 플랫폼(Android NSD, macOS Bonjour)마다 동작 차이를 라이브러리가 감추고 있어 문제가 생기면 오히려 디버깅이 어렵다.

### ② UDP 멀티캐스트 직접 구현 (최초 설계) — 채택 후 개정

5초마다 그룹 주소로 announce를 멀티캐스트하고, 받은 쪽이 유니캐스트로 응답하고, 15초 무소식이면 목록에서 제거(TTL)하는 구조를 직접 구현했다. mac ↔ mac에서는 완벽히 동작했다.

**그러나 실기기(mac ↔ Android)에서 실측한 결과, 소비자 공유기 상당수가 mDNS 그룹(224.0.0.251) 외의 멀티캐스트를 무선 구간에서 버린다.** 유선·루프백에서는 되고 Wi-Fi를 건너면 안 되는, 코드로는 원인을 알 수 없는 실패였다. 같은 패킷을 서브넷 브로드캐스트 주소로 보내면 도달함을 확인했다.

### ③ 멀티캐스트 + 브로드캐스트 병행 (개정) — 최종 채택

announce를 멀티캐스트와 서브넷 브로드캐스트로 **둘 다** 보낸다. 브로드캐스트 주소는 인터페이스 넷마스크로 계산하되, 넷마스크를 못 얻는 런타임(dart:io)에서는 /24를 가정한다. 수신 측은 두 경로로 중복 도착하는 announce를 기기 지문(fingerprint) 기준 upsert(있으면 갱신, 없으면 추가)로 자연 흡수한다. 모든 피어 구현(Dart·Go·Rust)이 따라야 하는 필수 사양으로 스펙에 반영했다.

추가로 실측에서 얻은 규칙 두 가지도 스펙이 됐다.

- 송신 소켓은 IPv4 인터페이스를 **순회하며 인터페이스별로** 보낸다. 기본 인터페이스 하나만 쓰면 VPN 가상 인터페이스(utun) 쪽으로 나가버리는 것을 실측했다.
- Android는 배터리 절약을 위해 멀티캐스트 패킷을 기본으로 버리므로 MulticastLock(멀티캐스트 수신을 허용해 달라는 OS 요청)을 잡아야 한다.

## 결과

**얻는 것**

- 소켓 수준의 탐색 메커니즘을 완전히 이해하고 통제한다. "왜 안 잡히는가"를 패킷 단위로 추적할 수 있었고, 그 결과가 브로드캐스트 병행이라는 스펙 개정으로 이어졌다.
- 멀티캐스트가 완전히 막힌 네트워크(공유기 AP isolation 등)도 IP 직접 입력 폴백(`POST /api/v1/info`로 기기 정보 교환)으로 커버한다.

**잃는 것·지켜야 할 것 (감수)**

- announce 트래픽 2배. 5초 주기의 작은 JSON이라 실측상 무시 가능한 수준.
- AP isolation(공유기가 무선 기기 간 통신 자체를 차단하는 설정) 환경은 원리상 해결 불가 — IP 직접 입력도 안 된다. README에 한계로 명시한다.
