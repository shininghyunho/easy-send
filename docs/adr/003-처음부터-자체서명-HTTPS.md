# ADR-003: 전송 채널은 처음부터 자체서명 HTTPS로 간다 — 스파이크로 HTTP 퇴로를 제거했다

- **상태**: 확정 (2026-08-15, M0 스파이크 PASS로 확정)
- **결정**: 파일 전송 채널을 v1부터 HTTPS(자체서명 인증서)로 한다. "일단 HTTP 평문으로 만들고 나중에 HTTPS로 교체"하는 단계적 접근을 쓰지 않는다. 단, 유일한 기술 리스크였던 "순수 Dart로 인증서 생성이 되는가"를 프로젝트 최우선 스파이크(M0)로 검증하고, 실패하면 HTTP로 후퇴하는 퇴로를 미리 정해뒀다.
- **대가**: 첫 마일스톤이 UI가 아니라 인증서 스파이크가 된다(눈에 보이는 진척이 늦음).

## 배경

보안 채널(HTTPS)은 이 앱 신뢰 모델의 토대다 — 기기 ID 자체가 인증서 지문이다(ADR-004). 문제는 순서였다. HTTP로 먼저 동작하는 것을 만들고 HTTPS를 나중에 얹을 것인가, 처음부터 HTTPS로 갈 것인가.

불확실성은 딱 하나였다: **서버·CA 없이, 순수 Dart만으로 자체서명 인증서(자기가 자기를 서명한 인증서 — 인증기관 없이 만들 수 있음)와 키쌍을 만들어 Dart 내장 TLS(`SecurityContext`)에 장착할 수 있는가.** 후보 라이브러리(`basic_utils`)는 있지만 실증 전이었다.

## 검토한 대안

### ① HTTP 선행, HTTPS는 나중에 교체 — 기각

전송 로직을 HTTP 평문으로 먼저 완성하고 보안을 뒤에 얹는 안. 눈에 보이는 진척이 빠르다.

**기각 이유: "나중에 교체"는 전면 재작업이다.** 신원 모델(지문 = 기기 ID)이 인증서에 붙어 있어서, HTTP로 만든 탐색·전송·신뢰 코드는 HTTPS 전환 때 신원 처리를 전부 다시 짜야 한다. 미루는 만큼 재작업 범위만 커진다.

### ② 처음부터 HTTPS + 최우선 스파이크 — 채택

불확실성이 라이브러리 하나에 몰려 있으므로, 그것만 먼저 검증(M0 스파이크)하고 통과하면 처음부터 HTTPS로 간다. 실패 시 퇴로(v1을 HTTP로 후퇴, HTTPS는 v1.5로 연기)를 스파이크 **전에** 문서로 정해둬서, 실패해도 프로젝트가 죽지 않게 했다.

**스파이크 결과 = PASS.** 확인된 사실:

- `basic_utils`로 RSA 2048 키쌍 + 자체서명 인증서 생성 → 만든 PEM이 `SecurityContext`(BoringSSL 기반)에 포맷 변환 없이 그대로 로드됨 → HTTPS 서버 기동·왕복 성공.
- TLS 채널에서 꺼낸 인증서 지문(SHA-256, hex 64자리)이 생성 시 지문과 일치 — 신뢰 모델의 전제가 성립.
- 키 생성은 앱 최초 실행 1회뿐이고 RSA 68~200ms로 충분히 빨라, 20배 빠른 EC P-256으로 갈아탈 필요 없음.
- 함정 1개: `basic_utils`가 내는 PEM은 줄 끝이 `\r\n`이라, 지문 계산 전에 줄별 trim이 필요하다(안 하면 base64 디코드 실패).

## 결과

**얻는 것**

- HTTP → HTTPS 전환이라는 예정된 재작업이 통째로 사라졌다. 탐색·전송·신뢰 코드가 처음부터 최종 형태다.
- 리스크를 코드 몇십 줄의 스파이크로 조기에 태워, 이후 마일스톤이 불확실성 없이 진행됐다.

**잃는 것 (감수)**

- 첫 산출물이 화면 없는 스크립트(스파이크)라 초반 체감 진척이 느리다.
- 자체서명 인증서이므로 브라우저식 CA 검증은 처음부터 포기 — 신원 보장은 ADR-004의 지문 검증이 담당한다.
